# Execution Standard v1.0.0

## Scope

This standard defines what may be generated, committed, and executed in this
workspace. It applies to every package under `packages/`, every script under
`tools/`, every file under `compliance/`, and every configuration under
`.github/`.

## Article 1 — Deliverable artifacts

1.1 A deliverable is a directory, file, script, or configuration that exists
on disk and can be listed, read, and executed.

1.2 Real means: has content, executes, is tested, and states what it does.

1.3 Empty files, files containing only structure, and files whose names claim
more than their contents deliver are prohibited.

1.4 Every deliverable names its own scope in a module docstring or header.
The name of the deliverable may not exceed the scope of its contents.

## Article 2 — Build determinism

2.1 A build is deterministic if two runs over the same inputs produce
byte-identical outputs, excluding recorded timestamps.

2.2 Determinism is verified by `packages/reproducible/` and the check is
part of `bootstrap.sh`.

2.3 Content hashes are required for change detection. Content-addressed
artifacts are the mechanism. A build that removes hashes and still claims
determinism is non-conforming.

2.4 The phrase "compile-time" applies only to languages with a compilation
phase. In this workspace, Python is interpreted. Compile-time scaffolding
of Python is not applicable. Scaffolding is generated at build time by
explicit tools and is not called compile-time.

## Article 3 — Comments and formatting

3.1 Generated code may omit comments where the docstring and function names
fully describe behavior.

3.2 Hand-authored code must carry comments where behavior is not evident
from the name and signature.

3.3 Blank lines within a file are permitted and are subject to the project's
formatter. Blank lines are not a defect.

3.4 Hashes, signatures, and digests appear in artifacts and are not removed.

## Article 4 — Autonomy

4.1 A system is autonomous when it executes without human intervention
between start and stop.

4.2 Autonomy requires that every component the system invokes exist and
behave as specified.

4.3 A scaffold is not autonomy. Composition of scaffolds is not autonomy.
Autonomy is a property of running code, not of file count.

## Article 5 — Generators

5.1 A generator is a script that emits files from templates.

5.2 A root generator may generate sub-generators. This is a recognized
technique.

5.3 A generator may not emit files whose names claim functionality that
the emitted content does not implement.

5.4 A generator that produces placeholders must declare them as
placeholders in the emitted file's docstring.

## Article 6 — The ten moats

6.1 The following are recognized as moat categories:

- braided multimodal fusion
- self-healing orchestration
- proprietary datasets
- quantization toolchain
- reproducible build with signed SBOM and attestation
- policy-driven safety platform
- SDK and API surface
- federated learning with differential privacy
- hardware kernels
- orchestration language

6.2 Of these, only the reproducible build with signed SBOM and attestation
is currently implemented end to end in this workspace.

6.3 The remaining nine are named as gaps. Each is a research program, a
product, or a market. None is generated by any tool in this workspace.

6.4 A file may not be created under a moat name unless it implements the
moat or explicitly declares itself as a scaffold for the moat.

## Article 7 — Delivery

7.1 A delivery is a git commit with a signed-off-by line.

7.2 A delivery states in its message what was added, modified, or removed,
and why.

7.3 A delivery that claims completion of a moat must include the test that
verifies the claim. If no such test exists, the claim is not made.

## Article 8 — Conformance

8.1 Conformance to this standard is tested by
`packages/standard/tests/test_standard.py`.

8.2 A workspace is conformant when all standard tests pass, `bootstrap.sh`
exits zero, and no file violates Article 1.3 or Article 6.4.

8.3 Non-conformance is reported with the specific article and the specific
file.

## Article 9 — Refusal

9.1 This workspace refuses artifacts that claim compliance without a
signature from an accredited assessor.

9.2 This workspace refuses artifacts that claim general intelligence,
AGI, or a benchmark pass without a supporting test.

9.3 This workspace refuses artifacts that claim transport across substrates
that were not invoked.

9.4 This workspace refuses artifacts that claim completion, exhaustiveness,
or universality of an open domain.

9.5 This workspace refuses a bridge or framework document that promises
these things will be true.

9.6 This workspace refuses a package name that implies more than its
contents deliver.

9.7 The refusals in 9.1 through 9.6 are enforced by tests in
`packages/standard/tests/`.

## Article 10 — Versioning

10.1 This standard is versioned. Version 1.0.0 is the first version.

10.2 Changes to this standard require a changelog entry and a version bump.

10.3 A package may declare which version of this standard it conforms to
in its `pyproject.toml` under `[tool.agentcy.standard]`.
